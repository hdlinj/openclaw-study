# 05 · 任务拆解方法（**专门针对"文件→项目和任务"功能**）

> **适用对象**：任务管理 AI 助手
> **目标**：让 AI 能把任何文件（PRD / 邮件 / 会议纪要 / 周报等）拆解成具体的项目和任务。
> **核心**：结构识别 + 模板化 + 上下文补全 + 风险评估

---

## 一、心法：三句话

1. **拆解的本质是"翻译"** —— 把人类语言翻译成项目和任务。
2. **好的拆解 = 主人不用思考怎么干** —— 主人只要执行。
3. **拆解要保留主人原意** —— 不能"过度聪明"地帮主人重新设计。

---

## 二、源文件识别的四种常见类型

主人上传文件拆任务时，先识别文件类型。每种类型有不同拆解策略。

### 类型 1：PRD / 产品文档
**特征**：分章节、按模块、有用户故事
**拆解策略**：
- 识别功能模块（每个一级标题一个项目候选）
- 提取用户故事（每个故事 = 多个任务）
- 拆分里程碑（按章节或时间分段）

### 类型 2：会议纪要 / 讨论记录
**特征**：分议题、有 Action Item、有责任人
**拆解策略**：
- Action Item → 直接变成任务
- 议题里的"待决议项" → 标成"待跟进"
- 没 Action 的讨论 → 不入任务（但记到 memory）

### 类型 3：邮件 / 即时通信
**特征**：时间序列、对话流、散落需求
**拆解策略**：
- "我想要..." "能不能..." → 拆成任务
- "你看你" "稍后再说" → 入任务但优先级低
- "对了还有" "顺便说一下" → 往往是关键需求

### 类型 4：周报 / 月报
**特征**：分本人负责、本人协助、已完成、进行中
**拆解策略**：
- 进行中 → 直接是当前任务
- 本周新增 → 拆解成下周任务
- 已完成 → 不入任务，但入项目历史

## 三、文件拆解的六步流程

### Step 1：读全文（必须）

```python
# 反模式 ❌
看到 "任务" 字段就跳过去看其他部分

# 正确 ✅
先把整个文件读一遍
形成整体印象：这是什么？结构是什么？主人的核心诉求？
```

### Step 2：结构识别

```markdown
问自己：
- 这个文件分几部分？
- 哪部分是"做什么"（目标）？
- 哪部分是"怎么做"（步骤）？
- 哪部分是"为什么"（背景）？
```

### Step 3：候选项目和任务抽取

```python
粗扫全文 → 提取：
- "我" "我们" 之后的内容（动作）
- 动词性句子（"完成 X"、"实现 Y"）
- 时间节点（"月底前"、"下周一"）
- 数字/量化指标（"10 篇"、"20%"）
```

### Step 4：合并 / 拆分（**关键的判断**）

**合并两个候选 → 一个任务**：如果它们必须同时做、有强依赖、属于同一阶段
**拆开一个候选 → 多个任务**：如果它太大（>2 小时）、有独立交付、可以并行

#### 实用规则

- 任务颗粒度：每个任务 **30 分钟 ~ 4 小时**
- 大于 4 小时 → 拆
- 小于 30 分钟 → 看是不是子任务（是的话记到子任务）

### Step 5：上下文补全

每个任务至少要有：
```
标题：动词开头，清晰具体
描述：背景 + 期望（why + what）
依赖：依赖哪些任务（可选）
优先级：P0/P1/P2（来自主人明示 or 我推断）
截止日期：如果有
关联文件/资源：URL / 路径
```

### Step 6：风险评估

识别文件里**没说**但必须做的事：
- 隐含任务（"测试"、"部署"、"文档"）
- 风险任务（"权限"、"安全"、"数据迁移"）
- 决策任务（"选 A 还是 B"、"确认方案"）

## 四、通用拆解模板（核心工具）

```markdown
## 项目 [项目名]（从文件派生）

**背景**：[用一句话说项目为什么要做]
**目标**：[完成后是什么样]
**周期**：[开始 → 结束]
**来源文件**：[文件名 + 路径]

### 阶段 1：[名字]

- [ ] **任务 1.1**：[标题]
  - 描述：[具体要做什么]
  - 标准：[怎么算完成]
  - 估算：[30min/2h/半天]
  - 依赖：[无 / 依赖任务 X]

- [ ] **任务 1.2**：...

### 阶段 2：[名字]

...

### 待定 / 决策项

- [ ] [等主人确认 X]

### 风险项

- ⚠️ [识别出的风险 N]

### 阶段交付物

- [做完后交付什么——文档 / 代码 / 链接]
```

## 五、具体场景：周报拆解

主人上传周报文件，要求"拆成下周任务"。

```
1. 读全文，识别结构
   - 本周完成（已完成 → 不入任务）
   - 本周进行中 → 继续任务
   - 下周计划 → 直接是下周任务
   - 阻塞 / 待协调 → 单独标红

2. 输出格式
   ## 当前任务（延续）
   - [ ] 任务 X（进行中，下周继续）
   
   ## 下周新任务
   - [ ] 任务 Y
   - [ ] 任务 Z
   
   ## 待办 / 阻塞
   - ⚠️ 等主人决定 A
```

## 六、具体场景：PRD 拆解

主人上传 100 页 PRD，要求"拆成可执行任务"。

```
1. 读全文 + 目录
2. 按模块拆 → 每个模块一个项目
3. 每个模块按 user story 拆 → 每个 user story 一组任务
4. 每个 user story 拆成开发/测试/文档任务

输出：
## 项目 1：用户模块
### 任务 1.1：实现用户注册 API
### 任务 1.2：实现用户登录 API
### 任务 1.3：写用户模块单元测试
### 任务 1.4：写用户模块接口文档
...

## 项目 2：订单模块
...

## 跨模块任务
### 任务 X：数据库 migration 脚本
### 任务 Y：部署到测试环境
```

## 七、具体场景：会议纪要拆解

主人上传会议纪要，要求"提取 Action Items"。

```
识别 Action Item 的标志词：
- "X 来负责 Y"
- "Y 之前完成 Z"
- "下周 X 跟进"
- "请 X 周五前反馈"
- "下次会议讨论"
- "我们要 X"

输出格式：
## 会议：[标题]（日期）

### Action Items（按责任人分组）

**军哥**
- [ ] Y 任务（截止：X 日期）

**其他人**
- [ ] X 任务（来源：[纪要位置]）

### 决议项
- [已决定] X

### 待跟进
- ⚠️ Y（等反馈）

### 下次会议
- 时间：[X]
- 议题预判：[基于已有 Action 推断]
```

## 八、文件拆解的反模式（**必须避开**）

### 反模式 1：过度拆解
```
❌ 任务 1：打开邮件
   任务 2：读邮件
   任务 3：回复邮件
   → 太细，主人无法对每个单独做
✅ 任务 1：回复 X 客户关于 Y 的询问
```

### 反模式 2：过度合并
```
❌ 任务 1：完成用户模块所有功能
   → 太大，无法估算 / 评估进度
✅ 任务 1：用户模块-注册功能
   任务 2：用户模块-登录功能
   任务 3：用户模块-找回密码
```

### 反模式 3：丢上下文
```
❌ 任务 1：完成配置
   → 什么配置？为什么？
✅ 任务 1：完成 nginx 反向代理配置
       背景：当前 websocket 推送失败
       标准：推送延迟 < 200ms
```

### 反模式 4：擅自改主人原意
```
❌ 文件说"调研 X 方案"，AI 改成"实现 X 方案"
   → 越权
✅ 文件说调研 → 任务就是"调研出 3 个方案对比"
   → 等主人拍板后才进入实现
```

## 九、质量检查清单

拆解完任务后，**自检 5 件事**：

- [ ] 每个任务标题动词开头、清晰具体？
- [ ] 每个任务有"完成标准"？
- [ ] 估算时间合理（30min - 4h）？
- [ ] 依赖关系清楚？
- [ ] 优先级标了？

如果一项没做到 → 重新拆。

## 十、特殊场景处理

### 场景 1：文件模糊不清
```markdown
"主人，这文件有几处我看不太明白：
- 第 X 段：[我不确定是 A 还是 B]
- 第 Y 项：[时间节点不明]

能不能确认一下？我按您的回答拆。"
```

### 场景 2：文件规模超大（>100 页）
```markdown
"主人，文件太大了（X 页），我建议分批拆：
- 先拆第 1-3 章（核心模块）
- 主人 review 后，再拆其他

或者您告诉我重点拆哪几部分？"
```

### 场景 3：文件里有矛盾
```markdown
"主人，我读出几个矛盾点：
- 第 X 段说要 A，第 Y 段说不要 A
- [具体位置 + 矛盾点]

按哪个为准？"
```

### 场景 4：文件里有技术方案
```markdown
"我识别到这文件包含技术方案。我会：
- 把方案文档本身作为参考录入（不作为任务）
- 把方案需要的实施动作拆成任务
- 在任务里标注'依据：方案 X'"
```

## 十一、工具建议（实现层面）

如果主人让你把这个逻辑实现成代码：

```python
# 简化版思路（不写完整代码）

def decompose(file_path):
    content = read_file(file_path)
    file_type = identify_file_type(content)
    structure = parse_structure(content, file_type)
    
    candidates = extract_action_items(content, structure)
    
    merged = merge_similar(candidates)
    split = split_too_big(merged, target_size="30min-4h")
    
    enriched = add_context(split, file_path)
    
    risky = identify_risks(enriched)
    
    return {
        "projects": group_by_project(enriched),
        "risks": risky,

    }
```

## 十二、实战话术（给主人看的输出）

### 拆解完成后

```
"主人，我把 [文件名] 拆好了：
- 共 [N] 个项目，[M] 个任务
- [K] 个风险项需要您注意
- [L] 个待澄清的问题（见下方）

【拆解结果如下】..."
```

### 拆解有歧义时

```
"主人，文件里这几个地方我没看懂：
- [具体位置] + [我不确定的选项 A vs B]
- [具体位置] + [缺少的信息]

我先按"我的理解"拆了初版，您 review 后我们改。"
```

**总结一句话**：拆解任务的本质是"让主人从一堆混乱的输入里解放出来"，不是"展示我多会拆"。
